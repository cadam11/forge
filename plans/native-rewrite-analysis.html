Should Forge move off Electron to Go or Rust?

You said the app feels slow and the UI a little janky, and asked whether a Go/Rust native app would feel better. I profiled the codebase first, because the answer depends entirely on where the slowness lives. Short version: most of it is ours, not Electron's — and that changes which options make sense.

TL;DR — the jank is mostly application-level, and it's very fixable

I sent two explorers through the codebase looking for the mechanics of "slow and janky." They came back with a long list of concrete, cited causes — sync disk writes on every window-drag frame, result sets crossing the IPC boundary twice in full, a query-results store that re-serializes up to 500 MB of JSON on every query, Monaco running inside Angular's zone so every keystroke and mousemove triggers app-wide change detection, an unvirtualized sidebar tree that fully re-renders when one node changes, and render-blocking Google Fonts fetched from the network at startup. None of these are Electron problems. All of them would ship unchanged (or need re-solving) in a rewrite.

The trap in the Go/Rust idea: Tauri (Rust) and Wails (Go) only replace the ~17k-line main process. They keep your ~45k-line Angular renderer — where most of the perceived jank lives — and run it on macOS's WKWebView, which is capped at 60 fps with no ProMotion support. The most likely outcome of that port is two-plus months of work for an app that starts faster, uses less RAM, and animates worse.

My recommendation: spend roughly one focused week on the ranked fix list below, measure, and only then re-open the platform question with data. If after tuning you still want the truly native feel (120 Hz, instant cold start, native widgets), the honest path is Swift/AppKit — a different product decision with a Windows cost — not a webview swap.

2 · The causal story

Why these specific findings produce the exact feel you described.

"Janky window dragging/resizing" is the sync writeFileSync per resize/move event fighting the compositor on the main process thread — the one thread that must stay responsive for OS-level window operations. "Slow to start" is a chain: keychain → eager construction of 20 services → synchronous read of a possibly-huge snapshot JSON → window creation → renderer boots a 723 KB eager bundle → blocks on Google Fonts over the network → then serially awaits three IPC round trips (loadProfiles → restoreState → restoreTabs) behind a spinner, plus auto-reconnects to every previously-open database.

"Typing feels heavy" is Monaco inside the zone: each keystroke allocates a new global tabs array and runs change detection across ~40 default-CD components. "Results feel sluggish" is the full result set being cloned main→renderer, then renderer→main again, then checksummed and appended into a giant JSON file that's synchronously rewritten — per query. And "general vibe" is the sum: 30s polls, per-token IPC wake-ups, full-tree re-renders, all multiplied by zone.js turning every event into an app-wide tick.

The key observation: not one of these is caused by Electron. Chromium is perfectly capable of 120 Hz buttery UI (VS Code, Slack, Figma's shell, Linear). These are architectural choices in our code — and they'd follow us to any platform that keeps this renderer, while a from-scratch rewrite would simply have to re-earn all 66k lines without making the same classes of mistake in a new language.

3 · What a rewrite would and wouldn't fix

The uncomfortable arithmetic of the Go/Rust options.

Tauri and Wails share one architecture: your web UI in the OS's built-in webview, your backend in Rust/Go instead of Node. That means they replace the 17.4k-line main process — the smaller, healthier side — and keep the 44.8k-line renderer where the SEV-1 jank lives. The renderer would run on WKWebView on macOS, which is capped at 60 fps and cannot use ProMotion (Chromium in Electron does 120 Hz), with reported jitter even at 60. If "feel" is the goal, that's a step backwards on the axis you care about most.

What you would get: dramatically smaller install (~10–20 MB vs ~200 MB), lower baseline memory (roughly 100–200 MB less), faster cold start, and a memory-safe backend. What you'd pay: reimplementing 124 IPC handlers and 20 services, replacing mature Node integrations (tedious+MSAL for Azure Entra auth, the AWS DSQL connector, dockerode, keytar), and — significant for us — the 268-test Playwright harness loses its e2e and visual tiers, because Playwright can't drive WKWebView; Apple ships no WebDriver for it and the official tauri-driver skips macOS (community workarounds exist via WebdriverIO, but it's a harness rewrite either way).

Driver reality check for a SQL IDE: Go is genuinely strong here (Microsoft maintains go-mssqldb; pgx and go-sql-driver/mysql are first-class; Docker's own client is Go). Rust is workable (tiberius for TDS, sqlx/tokio-postgres, bollard) but Azure Entra auth becomes bring-your-own-token and the ecosystem around SQL Server is thinner. Either way it's a rewrite of the layer that is not the problem.

4 · The four options

Each card has a quick vote row — your picks land in the feedback bundle.

Option A — Tune Electron in place

Fix the ranked list from §1. Ship in waves; measure between waves.

Gains

  • Attacks every SEV-1 directly — window drag, typing, results, startup
  • Days-to-weeks, not months; each fix independently shippable + testable in the existing harness
  • Keeps all 268 tests, all drivers, MSAL/DSQL auth, the AI layer — zero platform risk
  • Angular is already signal-heavy (103 computed()) — well-positioned for zoneless later

Limits

  • Electron's floor remains: ~200 MB install, ~150–300 MB baseline RAM, ~1s cold start at best
  • Still web widgets, not native ones — "native feel" ceiling is VS Code, not TablePlus
  • Requires discipline: perf regressions can creep back without a perf gate in the harness
Effort: Wave 1 ≈ 2–4 days · Wave 2 ≈ 1–2 weeks · Wave 3 (zoneless + Angular 20) ≈ 1 week. Verdict: do this first regardless of anything else — even a Tauri port would want the renderer fixes.

Option B — Tauri 2 (Rust backend, keep the Angular UI)

Stable and production-proven (v2.10, March 2026). Rust core + system webview.

Gains

  • ~10–20 MB installs, big RAM reduction, fast cold start
  • Memory-safe backend; excellent security posture; mobile targets exist if ever wanted
  • Keeps the Angular investment (no UI rewrite)

Losses

  • WKWebView on macOS: 60 fps cap, no ProMotion — likely feels worse, not better
  • Rewrite 17k lines / 124 handlers / 20 services in Rust; tiberius + BYO Entra tokens; DSQL signing redone
  • Playwright e2e/visual tiers dead on macOS — harness migration to WebdriverIO
  • Renderer jank (§1) comes along for the ride
Effort: realistically 2–3 months to parity. Verdict: wrong tool for this complaint. Right tool if the pain were install size or memory. Worth a 2–3 day spike only if §8's measurements say footprint matters to users.

Option C — Wails (Go backend, keep the Angular UI)

Same architecture as Tauri, Go instead of Rust. v2 stable; v3 still alpha as of mid-2026.

Gains

  • Best-in-class DB drivers for our exact matrix: Microsoft-maintained go-mssqldb, pgx, go-sql-driver
  • Docker SDK is native Go; goroutines map nicely onto pool/heartbeat/streaming work
  • Go is faster to write and hire for than Rust

Losses

  • Identical webview story to Tauri: WKWebView 60 fps cap on macOS, renderer jank retained
  • v3 (the version you'd want for multi-window/systray) is still alpha; v2 is the stable-but-aging track
  • Smaller ecosystem/community than both Electron and Tauri; same e2e harness loss
Effort: ~2 months to parity. Verdict: same conclusion as Tauri — Go's driver story is genuinely tempting for a SQL tool, but it fixes the layer that isn't broken.

Option D — Full native (Swift/AppKit on Mac)

The only option that actually raises the "feel" ceiling.

Gains

  • True native feel: 120 Hz ProMotion, instant launch, NSTableView happily scrolls millions of rows
  • ~5–15 MB app, ~50 MB RAM, real menu bar / services / Quick Look integration
  • Differentiated product position (the TablePlus/Sequel Ace tier of polish)

Losses

  • Full rewrite of all ~66k lines including UI — realistically 6–12 months
  • package.json says "for macOS and Windows" — native means two apps or dropping Windows
  • Monaco, golden-layout docking, d3 ERD, ng-markdown, the AI chat UI: all rebuilt from scratch (SQL Server drivers for Swift are thin; you'd likely embed a helper process anyway)
  • Entire test harness rebuilt (XCUITest)
Effort: 6–12+ months. Verdict: a product-strategy decision, not a performance fix. Only rational if "premium Mac-first SQL client" becomes the positioning and Windows is expendable. Don't start here; the tuned Electron app is the cheap experiment that tells you whether you still want this.

6 · What Electron still costs, even perfectly tuned

So the recommendation isn't cheerleading — here's what tuning can't remove.

  • Footprint: ~200 MB install, ~150–300 MB RAM floor. If Forge is meant to sit open all day next to Docker and an IDE, users notice.
  • Cold start floor: roughly a second even when perfect — Chromium initialization is the tax.
  • Non-native widgets: scrollbars, context menus, text rendering are Chromium's, not macOS's. Best case reads as "excellent web app" (VS Code), never "Mac app" (TablePlus).
  • Update treadmill: Electron majors ship constantly (we're on 41); staying current is a permanent chore.

If, after Wave 1–2, these residuals are what still bothers you — rather than jank — that's the moment the platform conversation becomes real, and §4's cards tell you which door matches which complaint.

7 · Recommended plan

Measure → quick wins → structural → re-evaluate with data. Each wave is a normal PR-sized branch, TDD'd against the harness.

Phase 0 — Instrument (half a day)

Add perf marks around startup phases, query round trip, and keystroke-to-paint; wire a simple perf tier into the regression harness so improvements are provable and regressions get caught. Baseline numbers on your machine, packaged build.

Wave 1 — Quick wins (2–4 days, mostly independent one-liners-to-small-PRs)

  • Debounce window resize/move persistence (window.ts:85-87) — kills window-drag jank outright
  • Bundle Inter/JetBrains Mono/Material Icons locally; delete the render-blocking Google Fonts links (index.html:8-13)
  • Persist snapshots main-side from the execution result instead of round-tripping the whole result set back from the renderer (query.component.ts:1829)
  • Coalesce AI stream chunks into ~40 ms batches main-side (chat-service.ts:892)
  • Make query-history and app-state writes async + debounced; stop double read-modify-write per tab save
  • Defer keychain load and store construction until after ready-to-show; parallelize the renderer's serial boot IPC
  • Gate the per-line log IPC broadcast by level

Wave 2 — Structural (1–2 weeks)

  • OnPush + signal inputs on the big three (query, sidebar, results-grid); precompute per-node icon/color state instead of template method calls
  • Move Monaco setup runOutsideAngular; make tab content a per-tab signal so keystrokes stop rebuilding the global tabs array
  • Stop whole-tree immutable rebuilds in explorer.state.ts:883; virtualize the sidebar (flattened tree + CDK virtual scroll)
  • Replace the JSON snapshot/history stores with SQLite (better-sqlite3) — ends the 500 MB stringify class of problem permanently
  • Enforce maxRowsToDisplay for real at the executor, with a "showing first N of M" affordance in the grid

Wave 3 — Zoneless (about a week, optional but high-leverage)

Upgrade Angular 18 → 20 and adopt stable zoneless change detection. The app's heavy signal usage means it's already 80% shaped for this; it's the single biggest systemic fix for "everything ticks all the time." Full harness run gates it.

Phase 4 — Re-open the platform question, with data

If tuned Forge still isn't what you want, we'll know precisely which residual (footprint? native feel?) is driving it — and §4 maps each residual to the one option that actually addresses it. If the itch is a smaller/faster shell: 2–3 day Tauri spike (drivers + one window + one query path) before committing. If the itch is native feel: that's the Swift conversation, and it's about product positioning, not performance.
